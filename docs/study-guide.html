Chapter 1

The big picture

StudyRAG solves one problem: a student has lecture PDFs and wants to understand them and test themselves on them. So the app has two features:

  • Ask the material: you ask a question and get an answer taken only from your slides, with the page number it came from.
  • MCQ quiz: the app writes multiple-choice questions from your slides, checks them, lets you take the quiz, and exports it.

Both features need the same thing first: the PDF has to be turned into small searchable pieces. That shared step is called ingestion, and the place the pieces are stored is the vector store. Everything else is built on top of it.

One ingestion pipeline and one vector store serve both features. The LLM is only called at the end.

What happens when you use the app

  1. Upload. The PDF is read page by page, cut into chunks of about 800 characters, each chunk is turned into a list of numbers (an embedding), and everything is saved in ChromaDB together with the file name and page number.
  2. Ask. Your question is turned into an embedding too. ChromaDB finds the 5 chunks whose embeddings are closest to it. Those chunks, plus strict instructions, are sent to the LLM, which writes an answer and cites the pages.
  3. Quiz. The app picks chunks (by topic, or spread across the lecture), asks the LLM to write questions as JSON, validates them, removes duplicates, checks every answer key, and shows you the quiz.
Key idea. The LLM never "reads the whole PDF". It only sees the few chunks we retrieve. That is what keeps answers grounded in your material, and it is also why retrieval quality matters so much.
Chapter 2

Core AI concepts

You need eight ideas to understand the rest of the guide. Each card gives the plain definition and how StudyRAG uses it.

LLM

A Large Language Model predicts the next piece of text. Give it instructions and context, and it writes a continuation: an answer, a list of questions, JSON.

Here: qwen3:4b-instruct through Ollama (local), or Claude through its API.

Hallucination

When an LLM states something confidently that is not true or not in its source. Small models do it more.

Here: we fight it by giving the model only retrieved text and telling it to refuse when the answer is missing.

RAG

Retrieval-Augmented Generation: first retrieve relevant text, then generate an answer from it. The model works like an open-book exam instead of from memory.

Here: the whole "Ask the material" tab.

Embedding

A list of numbers (384 for our model) that represents the meaning of a text. Texts with similar meaning get similar numbers, even in different languages.

Like GPS coordinates for meaning: "UDP header size" and "حجم رأس UDP" land close together.

Cosine similarity

How we measure "close". It compares the direction of two embeddings: 1 means same meaning, around 0.7 for unrelated text with this model.

Here: ChromaDB is created with hnsw:space = cosine; we show it as the "similarity" score in Sources.

Vector store

A database that stores embeddings and can quickly find the nearest ones to a query embedding.

Here: ChromaDB, saved on disk in data/chroma, one collection per PDF.

Chunking

Cutting a long document into small pieces before embedding. Too big and the meaning gets blurred; too small and the context is lost.

Here: ~800 characters with 150 characters of overlap, never crossing a page.

Structured output

Making the LLM answer in a fixed format (JSON with known fields) so code can read it. Then we validate it, because models still make mistakes.

Here: Ollama's format option plus Pydantic models in schemas.py.

A tiny cosine example

Imagine embeddings with only 2 numbers. A = (0.8, 0.6) for "UDP header is 8 bytes", B = (0.6, 0.8) for "size of the UDP header", C = (−0.6, 0.8) for "the three-way handshake".

cos(A, B) = 0.8·0.6 + 0.6·0.8 = 0.96   # very similar
cos(A, C) = 0.8·(−0.6) + 0.6·0.8 = 0.00 # unrelated

When vectors are normalized (length 1), cosine similarity is just the dot product. That's why the code always passes normalize_embeddings=True: it makes the comparison fast and fair.

Temperature

Temperature controls randomness. 0 means "always pick the most likely word" (repeatable); higher values mean more variety. We use 0.2 for answers (factual), 0.4 for writing questions (some variety), and 0.0 for checking answers (we want the most consistent judgment).

Step 1: extract text page by page

core/ingest.py · extract_pages
with fitz.open(stream=pdf_bytes, filetype="pdf") as doc:
    return [(i + 1, unicodedata.normalize("NFKC", page.get_text("text")))
            for i, page in enumerate(doc)]

We keep a list of (page_number, text) pairs. Page numbers start at 1 because that's what a student sees in their PDF viewer.

NFKC normalization is there because of a real bug. Many PDFs store Arabic as "presentation forms": special codes for the shape a letter takes at the start, middle or end of a word (for example U+FEE3 instead of the normal letter م). They look identical on screen but are different characters, so the embedding model didn't recognize them and Arabic search failed. NFKC converts them back to normal letters. It also turns ligatures like "ﬁ" into "fi".

Step 2: detect empty or scanned pages

A page with fewer than 30 characters of text (MIN_PAGE_CHARS) is recorded as empty. Scanned PDFs are just images, so they have no text at all. IngestResult.warning turns this into a clear message: no text at all means "run OCR first"; half the pages empty means "only the text pages were indexed".

Step 3: chunk each page

We chunk page by page, never across pages. That way every chunk belongs to exactly one page, so citations are always exact. The cost is that a sentence split across two pages is split in the index too; we accepted that trade-off because exact page citations matter more for studying.

The splitter is recursive: it tries to cut at the biggest natural boundary first, and only uses a smaller one if a piece is still too long.

SEPARATORS = ["\n\n", "\n", ". ", "? ", "! ", "؟ ", "، ", "; ", " ", ""]
#              paragraph → line → sentence (incl. Arabic ؟ and ،) → word → characters
  1. Split. _split_recursive splits on the first separator that appears in the text. Any piece still longer than 800 characters is split again with the next, smaller separator. "" is the last resort: a hard cut every 800 characters.
  2. Merge. _merge glues the small pieces back together into chunks of up to 800 characters. When a chunk is full, it keeps the last ~150 characters and starts the next chunk with them. That shared text is the overlap.
  3. Clean. Chunks shorter than 20 characters (like a lone page number) are dropped.
Why overlap? If a key sentence sits right at a cut, without overlap half of it would be in one chunk and half in the next, and neither would match a question well. With overlap, the boundary text appears in both chunks.

Try it: chunking playground

This is the same algorithm as split_text, ported to JavaScript. Change the size and overlap and watch the chunks change. Highlighted text at the start of a chunk is the overlap carried over from the previous one.

The app itself uses 800 / 150. With those settings this page of the lecture becomes two chunks (you can set the sliders to check).

Step 4: embed with the right prefix

def embed_passages(texts):
    # e5 models are trained with "passage: " / "query: " prefixes.
    return get_embedder().encode([f"passage: {t}" for t in texts],
                                 normalize_embeddings=True, batch_size=32).tolist()

def embed_query(text):
    return get_embedder().encode(f"query: {text}", normalize_embeddings=True).tolist()

The e5 model family was trained to see passage: before stored text and query: before questions. Leaving the prefixes out still works, but noticeably worse. It's a small detail that many tutorials miss.

Step 5: store in ChromaDB

doc_id = "doc_" + hashlib.sha1(pdf_bytes).hexdigest()[:16]
col = client.get_or_create_collection(
    doc_id, metadata={"filename": filename, "n_pages": len(pages), "hnsw:space": "cosine"})
col.add(ids=[f"{doc_id}-p{page}-c{i}" ...], documents=[...], embeddings=[...],
        metadatas=[{"filename": ..., "page": ..., "chunk_index": ..., "doc_id": ...}])
  • One collection per PDF. The brief asked for it, and it makes "pick which documents to work on" and "delete a document" trivial.
  • The collection name is a hash of the file's bytes, not its name. Uploading the same file again (even renamed) finds the existing collection and skips the work. That's the already_indexed path.
  • Metadata (filename, page) is stored with every chunk. That's what makes citations and page-range filters possible.
  • Batches of 32 chunks are embedded at a time, so the progress bar can move and memory stays low.
Chapter 5 · core/retriever.py

Retrieval: finding the right chunks

Retrieval has three functions. Both features use them.

retrieve(query, doc_ids, k=5, page_range=None)

q_emb = embed_query(query)
for doc_id in doc_ids:                       # one search per selected PDF
    res = col.query(query_embeddings=[q_emb], n_results=min(k, n),
                    where=_page_filter(page_range), ...)
    hits += [...]                             # score = 1 - cosine distance
hits.sort(key=lambda h: h["score"], reverse=True)
return hits[:k]                               # best k across ALL documents

Because there is one collection per PDF, we search each selected collection, collect all hits, sort them by score, and keep the best k overall. Chroma returns a distance (0 = identical); we convert it to a similarity (1 − distance) because "higher is better" is easier to read in the Sources panel.

The page filter is a Chroma where clause on the metadata:

{"$and": [{"page": {"$gte": 2}}, {"page": {"$lte": 4}}]}

all_chunks() and sample_spread(doc_ids, n)

For a quiz with no topic, we don't want 10 questions about page 1. sample_spread gets every chunk in reading order and takes n of them at equal steps, so the quiz covers the whole lecture.

step = len(chunks) / n
return [chunks[int(i * step)] for i in range(n)]   # e.g. 14 chunks, n=5 → indexes 0, 2, 5, 8, 11
Real numbers from the sample. For "How big is the UDP header?" the top hit was page 3 with similarity 0.85. For an unrelated question ("capital of France?") the best score was only 0.73. Even irrelevant text scores around 0.7 with e5 models, so a fixed "minimum score" filter is risky. That's why refusing unrelated questions is left to the prompt (Chapter 6).

RAG Q&A: answering from your slides

1. Detect the language

def detect_language(text):
    return "ar" if len(_ARABIC.findall(text)) > len(_LATIN.findall(text)) else "en"

We count Arabic letters vs Latin letters. A question like "ما هو TCP؟" has more Arabic letters, so it's Arabic. The language name is then written into the prompt ("Write the whole answer in Arabic"). Small models follow an explicit instruction much better than "answer in the same language as the question".

2. Handle follow-up questions

if history and len(question.split()) < 6:
    prev = last user question
    return f"{prev} {question}"      # used only for retrieval

"And what happens on a timeout?" contains no topic words, so searching for it alone finds nothing useful. For short questions we search with the previous question glued in front. The last 2 exchanges are also included in the prompt so the model understands what "it" refers to.

3. The prompt

The system prompt holds the rules; the user prompt holds the data. Here is the real system prompt:

You are StudyRAG, a careful study assistant for a college student.
Rules:
1. Answer ONLY with information found in the CONTEXT excerpts. Do not use outside knowledge.
2. If the CONTEXT does not contain the answer, reply with exactly this sentence and nothing else:
   "I couldn't find the answer to that in the selected material."
3. After each fact, cite its excerpt label exactly as written, e.g. [lecture.pdf p.3].
4. Write the whole answer in English.
5. Be concise and clear: a short paragraph or a few bullet points.

Each retrieved chunk is put in the CONTEXT with a label, [networks_lecture.pdf p.3], and the model is told to copy that label as its citation. This is the simplest reliable citation method: the model doesn't have to invent a format, only copy one.

4. Three layers against hallucination

  1. No chunks at all (no documents selected, or empty): we don't even call the LLM; we return the fixed "not found" sentence.
  2. The prompt rule tells the model to answer only from the context and to use the exact refusal sentence otherwise.
  3. is_not_found() checks whether the answer starts with that refusal sentence. If it does, the UI hides the citations and Sources, so the student isn't shown "sources" for an answer that doesn't exist.

In testing, "Who invented the World Wide Web?" and "Who won the 2022 World Cup?" were both correctly refused.

5. Streaming and the citation line

The UI calls llm.stream() so words appear as they are generated. After the answer, _cite_line() in app.py finds all [file p.N] labels with a regex and shows them as a "📎" line. If the model forgot to cite, it falls back to listing the retrieved pages.

Known weakness. A 4B model sometimes cites the wrong neighbouring page (for example, a fact from p.7 cited as p.4). The Sources panel exists so the student can always see the real text and page.
Chapter 7 · core/mcq.py + schemas.py

The MCQ generator

This is the most engineered part of the project. A question that is badly worded, has two correct answers, or has the wrong answer marked is worse than no question, because it teaches the student something false. So generation is a pipeline of checks.

flowchart TD
  S["select_chunks

  L -- no --> A["_ask: LLM writes 5 questions
JSON schema enforced"]
  A --> V["parse_mcqs: Pydantic
one retry on failure"]
  V --> P["attribute_pages

  P --> SH["shuffle_options"]
  SH --> D["dedupe
cosine ≥ 0.93"]
  D --> BS["verify: blind-solve
keep if only the key is correct"]
  BS --> L
  L -- yes --> OUT["first n questions"]

Step 1: choose the material

  • With a topic: retrieve(topic), then keep only chunks within 0.05 similarity of the best hit (TOPIC_SCORE_MARGIN). Without this, a short lecture would return every chunk and the "UDP" quiz drifted into TCP questions. We saw exactly that in testing.
  • Without a topic: sample_spread for even coverage.

Step 2: generate in small batches

Each LLM call gets 3 chunks (~2,400 characters) and is asked for 5 questions. Small models do much better with short context and small tasks than with "write 30 questions from this whole PDF". The loop walks through the chunk pool so successive batches cover different parts. The prompt also lists the questions already written ("Do NOT repeat these…").

With Ollama, the JSON schema is passed as format. That's constrained decoding: Ollama only lets the model produce tokens that keep the output valid against the schema, so broken JSON becomes almost impossible.

Step 3: validate with Pydantic

Each question is validated separately: one bad question is dropped, the good ones in the same batch are kept. If nothing usable came back, we retry once, appending the error messages to the prompt so the model knows what to fix, with a lower temperature (0.2).

Step 4: attribute the source page

c_emb = encode(["passage: " + chunk text ...])
q_emb = encode(["query: " + question + correct answer ...])
best = argmax(q_emb @ c_emb.T)          # most similar chunk for each question
source_page = chunks[best]["page"]

We ask the model for source_page, but we don't trust it. In testing it wrote "4" because the fact was in Excerpt 1 of a batch whose pages were 4, 7 and 9, while the real page was 9. Matching the question plus its answer against the batch's chunks by embedding gives the right page every time.

Step 5: shuffle the options

Small models put the correct answer under "A" far too often. shuffle_options shuffles the 4 options and recomputes which letter is correct, so the answer key is balanced. A seeded random.Random makes it repeatable in tests.

Step 6: remove duplicates

Exact duplicates are caught by comparing normalized text. Near-duplicates ("Which port does HTTPS use?" vs "What port is used by HTTPS by default?") are caught by embedding similarity: if a new question has cosine ≥ 0.93 with any question already kept, it's dropped.

Step 7: the blind-solve check

This is the most important idea in the project. Valid JSON tells you the format is right, not the answer. In testing, perfectly valid questions had the wrong letter marked as correct, or two true options. Pydantic can't see that.

So after generating a batch, we send the questions without the answer key back to the model, with the same excerpts, and ask a different question: "List every option that is correct according to the excerpts."

reviews = {1: {"B"}, 2: {"A", "C"}, 3: set(), ...}
keep q  only if  reviews[i] == {q.correct}      # exactly one correct, and it's the key
Review saysMeaningResult
{"B"}, key is Bone correct answer, matcheskept
{"C"}, key is Bthe key is probably wrongdropped
{"A", "B"}ambiguous: two true optionsdropped
{}no option supported by the textdropped
Design choices to remember.
  • Shuffle before verifying, so the reviewer can't lean on the "answer is usually A" habit.
  • Temperature 0.0 for the review: we want its most consistent judgment.
  • Fail open: if the review itself comes back unreadable, we keep the batch instead of throwing everything away. It's a trade-off: never returning an empty quiz vs. occasionally letting an unchecked question through.
  • Over-generate: each batch always asks for 5 even if we need fewer, because some get rejected. Extras are trimmed at the end.

For 10 questions: ceil(10/5) = 2 normal rounds + up to 4 extra rounds. If the material simply doesn't have enough distinct facts, the app returns fewer questions and the UI says so, which is better than padding the quiz with bad questions.

Difficulty levels

Difficulty is a description injected into the prompt (DIFFICULTY_GUIDE in prompts.py): easy = recall one stated fact; medium = explain why/how, compare, apply a rule; hard = multi-step reasoning or a scenario, with common misconceptions as distractors.

Chapter 8 · core/llm.py

The LLM wrapper

The rest of the code never talks to Ollama or Claude directly. It calls three functions:

FunctionUsed byDoes
generate(system, user, json_schema=None, temperature)MCQ, verification, evalOne full answer as a string.
stream(system, user)Chat tabYields the answer piece by piece.
health()Sidebar 🟢 / 🔴Is the server up and the model installed?

This is the adapter pattern: one interface, several back-ends, chosen by LLM_PROVIDER in .env.

Ollama

POST http://localhost:11434/api/chat
{
  "model": "qwen3:4b-instruct",
  "messages": [{"role": "system", ...}, {"role": "user", ...}],
  "stream": false,
  "format": { ...JSON schema... },        # only for MCQ / verification
  "options": {"temperature": 0.4, "num_ctx": 8192, "num_predict": 4096}
}

num_ctx: 8192 matters: Ollama's default context on a 4 GB GPU is only 4096 tokens, which can cut off the excerpts plus the list of already-written questions.

Claude

Uses the official anthropic SDK. Claude has no format option here, so the JSON schema is appended to the prompt as text ("Return ONLY a JSON object matching this schema"). Our tolerant _extract_json also strips ```json code fences if they appear.

The fake provider

LLM_PROVIDER=fake returns predictable answers built from the prompt itself: questions made from sentences in the excerpts, and a reviewer that "knows" which option was quoted. It means all 120 tests run in about 20 seconds with no GPU and no model. That's a common professional technique: make the slow, unpredictable dependency swappable.

Thinking models

Some models write their reasoning before the answer, between <think> tags. strip_think() removes it from full answers, and _skip_think() swallows it from the stream. OLLAMA_THINK=false asks Ollama to turn thinking off for models that support switching it.

Chapter 9 · app.py

The Streamlit app

The one thing to understand about Streamlit

Every click re-runs the whole script from top to bottom. Typing a question, ticking a radio button, pressing a button: Streamlit runs app.py again and redraws the page. Two tools make that workable:

ToolWhat survives a rerunUsed for
st.session_statePer-user valueschat history, the current quiz, whether it's submitted, which uploads were already processed
@st.cache_resourceShared heavy objectsthe embedding model (loaded once, not on every click)

Example: without ss.ingested, every rerun would see the uploaded file again and re-process it. We store (file name, size) of processed uploads to skip them.

Pages: a shell plus views

app.py uses st.navigation to build a menu of three pages and runs the selected one with pages.run(). Everything shared (the sidebar, the selected documents) is set up in app.py before the page runs, and stored in session_state (selected_docs, doc_names, max_pages) so each page can read it.

A Streamlit trap we avoided. When you switch pages, Streamlit deletes the values of widgets that are no longer on screen, so quiz answers would be lost. Each radio button has an on_change callback that copies the answer into ss.answers, a plain session value that survives, and the radio is re-created from it.

The progress database (core/store.py)

When you submit a quiz, store.record_attempt() saves one row in quiz_attempts (date, documents, difficulty, topic, score) and one row per question in question_results (document, page, your answer, correct or not, and the full question as JSON so it can be asked again later).

  • Migrations: the schema is a numbered list; SQLite's PRAGMA user_version remembers how many have run. Later phases add tables by appending to the list, without losing your history.
  • A connection per call: simple, and safe with Streamlit's multiple threads.
  • page_stats() groups results by document and page and sorts the weakest first. The Progress page uses it for the "Pages to review" list, and Phase 2 builds "quiz me on my mistakes" on top of it.
  • Questions now carry source_doc and source_file, set by attribute_pages, so a page number is never ambiguous when several PDFs are selected.

Layout

  • Sidebar: title, LLM status (🟢 / 🔴 with a fix-it message), uploader with progress bar, the "Work on" document picker, and a Manage section to delete a document.
  • Ask page: the conversation in a container above the input box, the citation line, and a "Sources" expander with the retrieved chunks and their similarity scores.
  • Quiz page: a form (number, difficulty, topic, page range), a progress bar while generating, then one radio group per question, Submit → score and explanations, Retake, and the three export buttons. Submitting saves the attempt to the progress database.
  • Progress page: totals, an accuracy-by-page chart, "pages to review" (below 60%), the quiz history table, and a review of any past quiz.

Details worth knowing

  • Arabic display: _markdown() wraps Arabic text in dir="rtl" and wraps citations in <bdi dir="ltr"> so the brackets don't flip.
  • Streaming then re-render: the answer streams into a placeholder (st.empty()), then the placeholder is replaced with the final, right-to-left-aware rendering.
  • Radio keys include quiz_id: "Retake" increments the id, which gives every radio a new key and clears all answers.
  • The quiz is stored as validated MCQ objects, not re-validated on every rerun (Chapter 12 explains the crash that taught us this).
  • .streamlit/config.toml disables the file watcher, which otherwise crawls torch/transformers and floods the log with harmless import errors.

Chapter 11 · core/study.py + core/exam.py

Study tools & exams (Phase 1)

PowerPoint and Word: the "unit" idea

A citation has to point somewhere a student can find. PDFs have pages, decks have slides, but Word files have no fixed pages (they depend on the printer and font). So every document gets a unit: page, slide or part, chosen by file extension in ingest.UNITS. One helper, fmt_ref(unit, n), produces p.3, slide 3 or part 3, and every screen uses it.

  • Slides (extract_slides): text from every shape, grouped shapes and tables, plus the speaker notes. In testing, "the algorithm behind RIP" was only in the notes, and it was answered correctly with [routing.pptx slide 1].
  • Word (extract_docx_parts): walks paragraphs and tables in document order; a new part starts at every heading, or after ~3,000 characters.
  • Documents indexed before this change have no unit in their metadata, so the retriever defaults to page. Old data keeps working.

Cheat sheet: map-reduce summarisation

A 4B model can't read a whole long lecture at once. If the material is under 9,000 characters it goes to the LLM in one call. Otherwise it's done in two steps:

  1. Map. Each ~6,000-character batch becomes short cited bullet notes (NOTES_SYSTEM).
  2. Reduce. The notes become one cheat sheet with four fixed sections (CHEATSHEET_SYSTEM), still with citations.

The result is cached in the database (study_notes table) under a key built from the tool, the document and the options. Opening it again is instant; "Regenerate" bypasses the cache.

Explain a page: getting real Arabic out of a small model

page_text() rebuilds the page from its chunks, removing the overlapping text between neighbours. The explanation streams next to the original.

Bug we hit. Asked to "write in Arabic but keep technical terms in English", the model did the opposite: English text with Arabic in parentheses, plus one wrong translation. Fix: put the language rule first in the system prompt with a concrete example, and end the request with a short reminder written in Arabic (ARABIC_REMINDER). Small models follow the last instruction, and the one in the target language, most reliably. The result went to 85–90% Arabic text, with correct terms such as "three-way handshake (المصافحة الثلاثية)".

Glossary and concept map: same pattern as the MCQs

Both use JSON from the LLM, validated by Pydantic before display:

  • GlossaryTerm requires the translation and the Arabic definition to actually contain Arabic letters. The source page is set by embedding similarity, exactly like MCQ pages.
  • ConceptMap removes duplicate ids, self-loops, duplicate links and links to unknown concepts. If more than a quarter of the concepts have no links, the code retries once and names the unconnected concepts in the retry message; unconnected concepts are then dropped. It's drawn with Graphviz DOT in the browser and can be exported as Mermaid.

The concept map is built from the English cheat sheet rather than the raw lecture, because the cheat sheet is already short and cited. That's one tool reusing another.

Exam simulation

  • split_counts turns "10 questions, 60% easy / 40% medium" into exact counts using largest-remainder rounding, so the total always matches (tested for every size from 5 to 40).
  • Each difficulty is generated with the normal MCQ pipeline; then duplicates across levels are removed and the order is shuffled.
  • The countdown is an @st.fragment(run_every=1): only that small piece re-runs every second, not the whole page. At zero it submits and calls st.rerun(scope="app"). If you were on another page when time ran out, the exam page submits as soon as you come back.
  • The source page is hidden during the exam (it would be a hint) and shown in the review.
  • Saved with mode="exam", the time used, and each question's difficulty (database migration 2).
Chapter 12 · grading.py + srs.py + cards.py

The learning loop (Phase 2)

Four question types, one generator

Multiple choice, true/false, fill in the blank and short answer each have a Pydantic model that inherits a shared base, Sourced (page, unit, document). Every type exposes the same three things: .question, .correct_text and .explanation. So de-duplication, page attribution, storage and progress work for every type with no special cases.

The generation loop in mcq.py is shared. What differs between types lives in a small Spec: the prompt, the JSON schema, the Pydantic model and the blind check. Adding a fifth type means adding one spec.

Bug we hit: outside knowledge. A fill-in question "The UDP header is _____ bytes long" was written from excerpts (p.1, p.4, p.7) that don't say it. The model knew it from training, and the blind check, being the same model, agreed. Fix: grounded_fill(), a plain-code check that the answer appears in the excerpts. A model can't catch its own outside knowledge; code can.

Grading (core/grading.py)

  • Fill-in answers are compared after normalize(): case, punctuation, "the/a/an", Arabic diacritics and number words ("eight" = "8") don't matter. Answers of 5+ characters may differ by small typos (similarity ≥ 0.85, using difflib).
  • Short answers go to the LLM with the question, the model answer, the key points and the lecture page. It returns a score of 0, 0.5 or 1, feedback in the student's language, and the missing points. Half credit counts as "correct" in statistics.

Practising weak spots

  • Retry my wrong answers uses store.mistakes(): for each question it takes the latest answer (MAX(id) … GROUP BY question) and keeps those still wrong. Answer one correctly and it leaves the list. No LLM needed, and multiple-choice options are reshuffled so you can't remember a letter.
  • New questions on weak pages passes a focus set of (document, page) pairs to the generator.
Bug we hit: four questions, one fact. In a mixed quiz each type was generated separately from the same first excerpts, so 4 of 5 questions tested "how is a TCP socket identified". Two fixes: each type receives the questions already written (avoid), and each type starts at a different point of the material (phase). The next run covered 5 different facts across 4 pages.

Spaced repetition: SM-2 (core/srs.py)

Each card stores an ease (starts at 2.5), an interval in days and reps (successful reviews in a row). The buttons map to grades: Again 1, Hard 3, Good 4, Easy 5.

forgot (grade < 3):  reps = 0, due again today          # Anki-style relearning
remembered:          interval = 1 day, then 6 days, then interval × ease
ease += 0.1 − (5 − grade) × (0.08 + (5 − grade) × 0.02)   # never below 1.3

Good, Good, Good  →  1 day, 6 days, 15 days (6 × 2.5)

Plain SM-2 shows "1 day" on all four buttons for a new card, which tells you nothing, so two Anki rules were added: Again keeps the card due today, and Easy on a new card jumps to 4 days. Cards come from the glossary (reused from the cache whatever its size; a cache-key mismatch first caused a 2.5-minute rebuild), from the lecture (LLM, validated, page-attributed), or from your mistakes. anki_package() builds a real .apkg with genanki; stable IDs mean re-importing updates the same deck.

Chapter 13 · retriever.py + citations.py + eval/

Measuring and improving quality (Phase 3)

Step 1: a benchmark that can actually fail

The original 10-question evaluation scored 10/10, so it could not show any improvement. A useful benchmark must be hard. The new one adds a second lecture (the network layer) that deliberately overlaps the first: four header sizes (TCP 20, UDP 8, IPv4 20, IPv6 40 bytes), two checksums, port numbers everywhere, Dijkstra and Bellman-Ford in both a PDF and a slide deck. 50 hand-written questions are split into four categories:

CategoryExampleWhat it tests
keyword"Which port does a DHCP server listen on?"exact terms and numbers
paraphrase"What stops a packet from circling forever between routers?" (answer: TTL)meaning without shared words
confusable"How long is an IPv4 header without options?"telling similar facts apart
arabic"ما هو حجم رأس IPv6؟"Arabic question, English slide

Step 2: four search modes, measured

Modehit@1MRR@5paraphraseArabictime
vector (e5)78%0.84857%60%0.04 s
keyword (BM25)76%0.83264%60%0.04 s
hybrid (RRF)82%0.87364%60%0.05 s
hybrid + re-rank90%0.93071%90%0.7 s
  • BM25 scores chunks by shared words, weighting rare words more (TF-IDF style). It is great for identifiers like SOCK_DGRAM or "port 67", and blind to meaning.
  • Reciprocal Rank Fusion merges the two lists using only ranks: score = Σ 1/(60 + rank). It needs no score calibration, because BM25 scores and cosine similarities are on different scales.
  • A cross-encoder re-ranker reads question and chunk together (one transformer pass per pair), so it judges relevance much better than comparing two separate embeddings. It is too slow for every chunk, so it only re-scores the ~10 fused candidates.
Finding: language bias. Arabic questions were stuck at 60% in every mode without re-ranking. Multilingual embeddings pull an Arabic question toward Arabic text, so the Arabic summary pages won over the English page with the answer. The cross-encoder judges relevance, not language similarity: 60% → 90%.

Ten re-rank candidates gave exactly the same accuracy as twenty at half the time, so the default is 10. If the re-ranker can't load (for example, a first run without internet), search falls back to hybrid and the sidebar says so.

Step 3: citation checking, and a failed first attempt

Real answers to all 50 questions were generated and their citations compared with the gold pages. Result: with hybrid + re-rank retrieval, the model's own citations were already 100% correct. The wrong page numbers seen earlier came from weaker retrieval.

The first checker made things worse. It "corrected" citations using embedding similarity and dropped accuracy from 100% to 94%: it moved a correct TTL citation to the wrong page and pushed Arabic sentences onto the Arabic summary page (the same language bias again). It was replaced, not shipped.

The current checker uses the re-ranker as the judge and is conservative: it replaces a citation only when the cited source clearly does not support the sentence and another source clearly does. To test it on errors, each correct citation was swapped for another retrieved page (an injection test). Result: 0 wrong corrections on clean answers and 56% of injected errors repaired. It also produced "unsupported sentence" flags, but 3 of 4 were true statements, so the UI doesn't show them: a warning that's usually wrong teaches people to ignore warnings.

The lesson for interviews. Measure before and after every "improvement". Two of the ideas here (an embedding-based citation fixer, and showing support warnings) looked good on paper and turned out harmful or noisy once measured.

Retrieval evaluation

eval/qa_pairs.json has 10 hand-written questions, each with the page that contains the answer (9 English, 1 Arabic). run_eval.py indexes the sample into a temporary DB and checks where the right page appears in the top 5.

Hit rate@5

Fraction of questions where the correct page is anywhere in the top 5. Measures "did we find it at all?"

MRR@5

Mean Reciprocal Rank: average of 1/rank of the correct page (1st = 1, 2nd = 0.5, 3rd = 0.33, missing = 0). Measures "how high did it rank?"

ranks of the correct page:  1, 1, 2, missing
hit rate = 3/4 = 0.75
MRR      = (1 + 1 + 0.5 + 0) / 4 = 0.625

Our result: hit rate 10/10, MRR 1.00 (the right page was first every time). The sample is small and clean, so this is a regression check: if a future change breaks retrieval, this number drops. To measure real quality, add questions about your own course.

Chapter 16

Self-test & glossary

Try to answer each question out loud before opening it. These are also the questions an interviewer is likely to ask about this project.

Fundamentals

What is RAG, and why use it instead of just asking the LLM?

Retrieval-Augmented Generation: retrieve relevant passages from your documents, then have the LLM answer using only those passages. The model doesn't know your specific lecture, may hallucinate, and can't cite pages. RAG grounds the answer in your material and makes citations possible.

What is an embedding, and how do we decide two texts are similar?

A vector of numbers (384 here) representing meaning. We compare vectors with cosine similarity; since we normalize them to length 1, that's just their dot product. Closer to 1 = more similar.

Why prefix texts with "passage: " and "query: "?

The e5 models were trained that way. Questions and passages are different kinds of text, and the prefixes tell the model which one it's embedding. Leaving them out reduces retrieval quality.

Why ~800 characters with 150 overlap, and why chunk per page?

800 characters is a few paragraphs: enough context to answer a question, small enough that one chunk is about one idea. Overlap prevents a key sentence from being cut in half at a boundary. Per-page chunking guarantees every chunk has exactly one page number, so citations are exact.

How does a multilingual model let an Arabic question find English content?

multilingual-e5 was trained so that texts with the same meaning get similar vectors regardless of language. "ما فائدة المصافحة الثلاثية" lands near the English chunk about the three-way handshake (we tested exactly this).

Design decisions

Why one Chroma collection per PDF, and what is the collection name?

The brief asked for it, and it makes selecting and deleting documents simple. The name is doc_ + the first 16 hex characters of the SHA-1 of the file bytes, so the same file uploaded twice (even renamed) is recognized and not re-indexed.

How does the app avoid hallucinating answers?

Three layers: no retrieved chunks → fixed refusal without calling the LLM; a prompt rule to answer only from CONTEXT and use an exact refusal sentence otherwise; is_not_found() detects that sentence and hides citations/sources. Plus the Sources panel lets the student verify any answer.

Why doesn't Pydantic validation guarantee good questions?

It checks structure (4 distinct options, a valid letter), not facts. A question can be perfectly valid JSON with the wrong letter marked correct, or with two true options. That's why the blind-solve verification exists.

Explain the blind-solve check. Why shuffle first, and why "fail open"?

The model re-answers each question without the key and lists every option it thinks is correct; we keep the question only if that set is exactly {the key}. Shuffling first stops the reviewer from benefiting from the "answer is usually A" bias. Failing open (keeping the batch if the review is unreadable) means a broken review never empties the quiz; the trade-off is that some unchecked questions can slip through.

Why compute the source page with embeddings instead of asking the model?

The model confused excerpt numbers with page numbers. Comparing the question plus its correct answer to each chunk in the batch is exact and cheap. General rule: don't ask an LLM for something you can compute.

Why different temperatures (0.2 / 0.4 / 0.0)?

Answers should be factual and stable (0.2). Writing questions benefits from some variety so batches don't repeat (0.4). The verification is a judgment and should be as consistent as possible (0.0).

What is constrained decoding?

Passing a JSON schema to Ollama's format option. While generating, Ollama only allows tokens that keep the output valid against the schema, so the model can't produce broken JSON. We still validate afterwards because the content can still be wrong.

Engineering

What is the fake provider for?

It makes the LLM swappable for a deterministic stub, so tests run in ~20 s with no GPU and always give the same result. Testing code that depends on a slow, random external service is otherwise unreliable.

Why the threading lock around the Chroma client?

Streamlit can run two script runs in parallel (a rerun starts while the first is still going). Both tried to create the persistent client at the same time, and one got a half-initialized instance. The lock ensures only one is ever created.

Explain Streamlit's rerun model and session_state.

Every interaction re-executes the whole script. Normal variables are lost each time; st.session_state keeps per-user values (chat, quiz) across reruns, and @st.cache_resource keeps heavy shared objects (the embedding model) loaded once.

Hit rate vs MRR?

Hit rate@k: did the right page appear anywhere in the top k? MRR@k: average of 1/rank of the right page, so it also rewards ranking it first. Hit rate tells you "found or not"; MRR tells you "how high".

Why do Word files cite "part 2" instead of a page number?

.docx files have no fixed pages: pagination depends on fonts, margins and the printer, so any page number we computed could be wrong. Splitting at headings gives stable, findable sections. Every document has a unit (page / slide / part), and one helper formats all citations.

How did you make a 4B model actually answer in Arabic?

The language rule moved to the start of the system prompt with a concrete example, and every Arabic request ends with a short reminder written in Arabic. Small models weigh the last instruction and the target-language text most. We measured the result: 85–90% Arabic letters.

Explain SM-2. What happens after Good, Good, Good, then Again?

Each card has an ease (2.5 at first), an interval and a count of successful reviews. Good, Good, Good gives 1 day, 6 days, then 6 × 2.5 = 15 days. Again resets the count to 0, lowers the ease (never below 1.3) and, with the Anki-style rule, makes the card due again the same day.

The blind check uses the same model. What can it NOT catch, and how did you handle it?

It can't catch facts the model knows from training that aren't in the lecture: the writer and the checker share the same knowledge. For fill-in questions a plain-code grounding check requires the answer to appear in the source excerpts. In general: use code for anything that can be checked exactly.

Why did hybrid search barely help Arabic questions, while re-ranking took them from 60% to 90%?

Both vector and keyword search were pulled toward the Arabic summary pages: embeddings because the language matches, BM25 because the Arabic words match. A cross-encoder reads the question and the passage together and scores relevance, so an English page that answers an Arabic question wins.

What is Reciprocal Rank Fusion and why use it instead of adding scores?

Each list contributes 1/(60 + rank) for every item; the sums decide the order. BM25 scores and cosine similarities live on different scales, so adding them needs calibration; ranks don't. Items found by both methods rise to the top.

How did you test a citation checker when the citations were already correct?

With an injection test: each correct citation was replaced by another retrieved page, and the checker had to repair it. That measures recall (56% repaired) separately from harm (0 false corrections on the clean answers).

How would you scale this to 1,000 PDFs?

One collection per PDF means one query per selected document, which gets slow. I'd move to a single collection with doc_id in the metadata and filter with a where clause; consider hybrid search (BM25 + vectors) and a re-ranker for quality; embed on a GPU or in background jobs; and possibly a server-based vector DB.

What would you improve next?

Built-in OCR for scanned PDFs; .pptx/.docx support; hybrid search and re-ranking; a larger evaluation set from real courses, including answer-quality scoring; flashcards and tracking weak topics over time.
